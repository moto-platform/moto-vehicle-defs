## [0.16.0] — 2026-10-18

MINOR, additive (the D-072 item 7 codegen follow-up and a moto_defs export). No DBC message, signal, ID, layout, scale, DID, `tester_policy`, frame gate or BLE change; every existing `*_pack()`, `*_is_in_range()` and `DIDS` entry keeps its behaviour. Consumers: moto-safety-node and moto-rt-core can send through the checked pack once they bump (rt-core: 0x120 and the other sent messages with a value table); moto-server can read `DID_STALE_AFTER_MS` instead of 3 x the poll period.

### Added
- codegen (`gen_c.py`): for every message a node sends that has a value table (VAL_), `gen/c/<node>/platform.{h,c}` gets `platform_<msg>_pack_checked(dst_p, src_p, size)`. It calls the existing `*_is_in_range()` of every signal and, for every enum signal, the new `platform_<msg>_<signal>_is_defined(value)` (the value table without `RESERVED` names; `is_in_range()` only knows the DBC min/max, which is wider, e.g. `NODE_MODE` [0|15] against 0..5 defined, and it accepts the `RESERVED` entries such as 0x120 lock request 1/2, 0x023 `CORNERING_SOURCE` 3 and 0x020 `LEAN_ANGLE_STATE` 2). If anything fails (or `dst_p`/`src_p` is NULL, or `size` is too small) it returns `-EINVAL` and writes nothing; otherwise it returns the plain pack's result. Raw 0 (no information) and `LOCK` = 3 pass; the reserved 0x120 lock requests 1 and 2, 0x023 `CORNERING_SOURCE` 3 and any undefined value are refused. One exit, no loops, no dynamic memory. The plain `*_pack()` still masks, as before. Each signal is checked on its own, not across fields (0x023 GREEN with source NONE, or UNAVAILABLE with EKF, are accepted; the `CORNERING_LEVEL` pairing is a safety-node unit test). **Review item for the rt-core / safety-node adoption PRs:** on a negative return `dst_p` is unchanged and must not be E2E-protected or transmitted; send the message's defined fallback (0x020 `LEAN_ANGLE_STATE` = INVALID, 0x023 all raw 0) or nothing. It is deliberately not fail-to-zero: raw 0 on 0x020 means 0 degrees ESTIMATED. The generated header doc says the same.
- codegen now fails on a signal whose raw `[min|max]` leaves its bit field, on a value-table key outside raw `[min|max]`, and on a value-table name that looks reserved (`Reserved`, `RESERVED_1`, `RSVD`, `RES`) but is not exactly `RESERVED`; `config.did_stale_after_ms()` raises on a non-integer YAML value.
- `gen/python/moto_defs/vehicle_cl250.py`: `DID_STALE_AFTER_MS` (name -> ms), from the same `config.did_stale_after_ms()` as the C table's `stale_after_ms` field. `DIDS` tuples are unchanged, so existing unpacking keeps working.
- Tests: `test_cantools_c.py` runs `pack_checked` on every sent enum message of every node (identical bytes to the plain pack for valid values, error and untouched buffer for every bad member, short buffers and NULL), the full C member type range (e.g. a 1-bit VALID at 2 and 3), two sentinel fills for "untouched", pack_checked -> `*_e2e_protect` -> `*_e2e_check` for every E2E message, synthetic-DBC tests for the new codegen refusals, plus the 0x023 and 0x120 cases; new `test_did_stale.py` compares the Python value with the compiled C table for every DID of every node that has it.

## [0.5.0] — 2026-10-03

Generated C encoders round to nearest (decision D-056, found while planning the rt-core platform-bus republisher, ISSUES D-5). No DBC, signal, ID, layout, scale, VSS path, DID, `tester_policy` or D-020 golden-copy change. Every generated `<msg>_<signal>_encode()` changes behaviour, so the same physical value can now produce a raw value one step higher than before: a MINOR release that each consumer bumps on purpose.

### Fixed
- codegen: cantools' C `<msg>_<signal>_encode()` truncated `(value - offset) / scale` toward zero, while the cantools Python reference (and every Python consumer) rounds. - tests (C-7): `encode()` now maps every raw value in the physical range back exactly (all of them up to 16 bits) and agrees with the Python reference for values up to 0.45 steps off, and returns the type limits past them (half a step, far, ±inf) and 0 for NaN, on every node, whether or not the node also has `decode()`.
