# MISRA C:2012 deviation register (`gen/c`)

`make misra` runs cppcheck (style checks + the MISRA C:2012 addon) over every node directory in `gen/c/` and **fails on any finding not listed here** (D-046 item 2). CI runs it on every push and pull request. `gen/c` carries the D-020 gates and is linked by safety-node, so generated C is held to the same rules as hand-written firmware. Mandatory rules have no deviations (MISRA Compliance:2020).

- **Fixes go into the codegen** (`tools/codegen/src/moto_codegen/`), never into `gen/` by hand. cantools has no MISRA mode, so `gen_c.py` (`_MISRA_FIXUPS`) rewrites the cantools patterns that break a required rule: 17.7 (`(void)memset`), 15.6 (braces on the `*_init()` NULL guard) and 10.8 (widen before masking in the `unpack_*_shift_*` helpers). These rewrites leave the machine code unchanged: at `-O2` every node's old and new `platform.o` are byte-identical, and the old and new helper expressions agree for every value, mask and shift under UBSan. `tools/codegen/tests/test_cantools_c.py` checks on a synthetic DBC that cantools still emits each pattern, that none survives the rewrite, and that the original and rewritten code both match cantools Python. Separately from the fixups, `_encode_rounding()` rewrites every `*_encode()` to round, saturate and map NaN to 0 (D-056); its body casts a plain `float` object, never a composite expression. The cppcheck addon does not categorise float operands, so it never reports 10.8 for a float-to-integer cast: that rule is kept by the codegen's construction, not proven by `make misra` (safety review MAJOR-1 on D-056).
- **Deviations:** file-scoped ones are in `suppressions.txt`, which names today's files. A single-line deviation would be an inline `/* cppcheck-suppress misra-c2012-<rule> ; DEV-xxx: <reason> */` comment emitted by a template. `tools/codegen/tests/test_misra_register.py` checks that every suppression names a DEV row here that covers its rule, and that no mandatory rule is deviated. Register, list and codegen change together, in the same PR, with a reason.
- **How the gate checks:**
  - It prints the cppcheck version.
  - It fails if the addon does not report 10.8, 15.6 and 17.7 on `canary.c`, so a missing or broken addon cannot pass as clean.
  - It models the 32-bit targets (`--platform=unix32`).
  - It also analyses each node's header-only files (`platform_limits.h`, `uds_iso14229.h`), which a directory scan would skip.
  - CI builds cppcheck 2.22.0 from source once, caches it, and pins the runner (Ubuntu 24.04), so the checker only changes on purpose. Ubuntu's apt cppcheck 2.13 misses findings that 2.22 reports: on `canary.c` it did not report 15.6.

|---|---|---|---|---|
| DEV-001 | 8.7 no external linkage if used in one unit (advisory) | every `.c` in `gen/c` | `gen/c` is a library. Its API is the cantools pack/unpack/encode/decode functions, the E2E library and wrappers, `vehicle_cl250_*` (DID table, functional watch list, D-020 gates) and `platform_uds_*`, plus the exported tables `vehicle_cl250_dids`, `vehicle_cl250_functional_watch`, `platform_uds_dids` and `platform_uds_dtcs`. File-internal helpers are `static` (cantools' shift helpers, `crc8_update()`). |
| DEV-002 | 2.5 unused macro (advisory) | the headers, `gen/c/*/*.h` | The headers are the generated interface: frame IDs, lengths, cycle times, signal limits and choices (cantools), E2E DataIDs and timeouts, DID and `tester_policy` constants, UDS IDs. Each consumer uses its own subset, so most macros are unused inside `gen/c`. | Every value comes from the definitions (`dbc/`, `uds/`, `limits/`), is checked by `moto-codegen check` and kept in sync by the drift test, so a consumer never writes the number itself (invariant 2). | DEV-003 | 2.3 unused type declaration, 2.4 unused tag declaration (advisory) | file scope: `vehicle_cl250.h`, `platform_uds.h`. No file in `gen/c` names the type, so cppcheck reports the typedef (2.3) and, for the same enum, 2.4. | The index enumerators are generated from the same list as the table they index (`enumerate()` in the same codegen run), so an index cannot drift from its table. `platform_uds_encoding_t` names the values of the DID table's `encoding` field. | DEV-004 | 15.5 single point of exit (advisory) | `platform.c`, `moto_e2e.c`, `platform_uds.c` | Early returns are argument guards and a lookup: cantools' size check in `*_pack()`/`*_unpack()` and NULL guard in `*_init()`, the status results of `moto_e2e_*()`, and the table lookup in `platform_uds_find_did()`. Same deviation as rt-core DEV-001. | `tools/codegen/tests/test_c_code.py` builds every node with `-Wall -Wextra -Werror -pedantic -Wshadow -Wconversion` and checks the E2E library against the Python reference, the BAD_ARGUMENT paths included. `test_cantools_c.py` runs every node's pack/unpack/init/decode against cantools Python: boundary values, 10 000 random payloads per message, `*_init(NULL)` and every short size (rejected, nothing written). |

The D-020 gate (`vehicle_cl250.c`) has no deviation. Since ISSUES C-6 its five functions have one exit each and `break`-terminated switch-clauses, so `make misra` checks it without a 15.5 suppression, and DEV-005 (16.1/16.3, `return`-terminated clauses) is closed; its ID is not reused. `test_gate_equivalence.py` proves the rewrite equal to the old gate (at `-O0` and `-O2`) over every byte the request and frame gates read and every data value of the table's DIDs; synthetic 3- and 4-byte entries are sampled. It checks that each gate function starts from `bool ok = false` (fail-closed: a path that forgets to assign refuses) and that each gate function keeps a single `return`, because cppcheck does not report 16.1/16.3 when a clause ends in `return`.

**Not decided by the tool here:**
- 12.2 through the `shift` parameter of cantools' helpers. cantools passes constant shifts that fit the type; the helper check above covers every shift.

Baseline at the switch to blocking (2026-10-01, cppcheck 2.22, all five nodes, before `unix32` and the header-only files were added): 678 × 8.7, 597 × 2.5, 165 × 15.5, 45 × 17.7, 28 × 15.6, 10 × 10.8, 6 × 2.3, 6 × 2.4 and 5 × `variableScope` (style). 17.7, 15.6, 10.8 (all required) and `variableScope` (in `moto_e2e_crc()`) were fixed in the codegen. The rest are DEV-001..DEV-004.
