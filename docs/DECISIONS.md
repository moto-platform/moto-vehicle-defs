**D-003 — Definition distribution: submodule + per-node codegen** (2026-09-25, user-approved)
Consumer repos pin `external/moto-vehicle-defs` as a git submodule to a **tag**. `tools/codegen` (built on cantools `generate_c_source`) generates, for each node, C code containing only the messages that node sends/receives. The output is committed under `gen/` before tagging, so the firmware build doesn't depend on Python and the generated code can be reviewed. Why: DBC/VSS can't be parsed on the MCU (F103 has 20 KB RAM); the generated code is `const` and malloc-free.

**D-004 — VSS only on the Raspi and above; mapping in the official VSS overlay format** (2026-09-25, user-approved)
Eclipse **kuksa-can-provider** is used for CAN→VSS. Mapping is done through the `dbc2vss` keys in the VSS overlay. The made-up `vss/mappings.yaml` format from the old `can-dbc-conventions` skill is **not used**. Motorcycle-specific signals are kept small and consistent under `Vehicle.Motorcycle.*`; the user is asked before every new extension. The safety path is never wired into VSS.

**D-005 — E2E protection on safety-critical platform messages** (2026-09-25, user-approved)
AUTOSAR E2E Profile 1/2-like scheme: 4-bit alive counter + CRC8 (SAE J1850) + an untransmitted DataID. The receiver checks timeout/counter/CRC. Scope: platform CAN 0x010-0x08F. Code is generated via codegen. Why: lets the safety node detect "data is late/frozen/corrupted"; cost is 1-2 bytes/message.

**D-006 — AUTOSAR: concepts yes, software stack no** (2026-09-25, user-approved)
Classic AUTOSAR BSW (commercial automotive toolchain + MCAL + hundreds of KB of flash) and Adaptive AUTOSAR are not used. The layer mapping (features≈SWC, services≈BSW, hal≈MCAL) and E2E are adopted. ARXML output can be generated from the DBC with canmatrix in Phase 2 (for showcase purposes).

**D-009 — Two separate CAN buses: vehicle (single read-only tester, D-037) + platform (dedicated)** _(bullets on safety-node/Raspi tapping the vehicle bus superseded by D-021; "hardware listen-only" wording superseded by D-037)_ (2026-09-25, Claude architecture proposal — revise if the user objects)
The architecture document stated both that "only the main MCU writes to the vehicle bus" (§4) and that io-node/rt-core publish status onto the vehicle bus (§5b.1, §5b.2); this was a contradiction. Resolution: our nodes talk on their own **platform CAN** bus. The vehicle bus is hardware listen-only; the sole exception is rt-core's OBD/UDS read requests. Why: this removes the risks of OEM ID collisions, confusing the OEM ECU, and added bus load; the two buses are simulated separately in HIL. The platform bus is classic CAN at 500 kbps (F103/ESP32 TWAI don't support FD). Details in `ARCHITECTURE.md` §3-4.

**D-019 — CL250 vehicle bus facts (verified on the real bike)** (2026-09-25, from `github.com/alihanesentas/HondaCl250_Telemetry`, whose CAN/UDS path was validated on the CL250)
- Diagnostic connector (DLC) CAN: **classic CAN, 500 kbps** (ESP32-S3 TWAI).
- ECU data is obtained by **polling**, not by passive broadcast: UDS `0x22 ReadDataByIdentifier`, 29-bit normal-fixed addressing request `0x18DA10F1` → response `0x18DAF110` (11-bit `0x7E0`/`0x7E8` also sent as a fallback).
- DIDs, OBD-mapped (`0xF4xx` = SAE J1979 PID), with J1979 scaling: `0xF40C` RPM = (A·256+B)/4 · `0xF40D` speed km/h = A · `0xF405` coolant °C = A−40 · `0xF411` TPS % = A·100/255 · `0xF442` battery V = (A·256+B)/1000.
- Session handling: `0x10 0x03` (extended session, retried until a positive `0x50`), and `0x3E 0x80` tester-present every 1000 ms.
- Still unknown: whether any passive broadcast traffic exists on this bus (Q-001 remains open only for that part).
Consequences: CL250 signals are defined as **vehicle DIDs in `uds/`** (not as broadcast messages in `cl250.dbc`). The allowed vehicle-bus services must include `0x10` (sub-functions 0x01/0x03 only) and `0x3E` → Q-011.

**D-020 — Vehicle-bus service allow-list** (2026-09-25, user; resolves Q-011) rt-core may send only `0x10` (sub-function 0x01 default / 0x03 extended), `0x3E` tester-present, `0x22`, `0x19`, and OBD `0x01/0x09` to the vehicle. Forbidden: `0x10 0x02` (programming), `0x11` ECU reset, `0x14` clear DTC, `0x27`, `0x2E`, `0x2F`, `0x31`, `0x34`, `0x36`, `0x37`. Why: the verified read path needs an extended session and tester-present (D-019); nothing that changes ECU state is allowed.

**D-025 — platform.dbc v0.1 message set** (2026-09-25, Claude proposal; user-confirmed 2026-09-26)
Safety range (E2E): `EkfLean` 0x020 / 20 ms, `VehicleSpeed` 0x021 / 50 ms, `EkfFrictionMass` 0x022 / 100 ms, all RT_CORE → SAFETY, LINUX (speed also CONN; since D-048 speed goes to CONN and LINUX only). Each EKF estimate carries a quality % and a 2-bit state (ESTIMATED / CLAMPED / DEFAULT fallback / INVALID, per hardware-architecture §5b.2); `VehicleSpeed` carries VALID + AGE (ms since the ECU sample) because the ECU speed DID is polled, not broadcast (800 ms in the legacy firmware, 100 ms provisional since D-029). Heartbeats 0x081-0x085 / 100 ms (E2E): NODE_MODE, ERROR_COUNT, UPTIME. State range: `VehicleEngine` 0x110 / 50 ms (RPM, battery, coolant, TPS with the J1979 source scaling, per-signal VALID + ECU_PRESENT). `E2E_DataID` convention `0x1000 + CAN ID`; `NodeId` is a BU_ attribute. CoG height and a cornering-warning output message are not defined yet (later MINOR). `uds/vehicle_cl250.yaml` gets a platform-chosen `stale_after_ms` = 3 × poll period per DID (not a legacy value). rt-core sends `*_STATE = INVALID`, `QUALITY = 0` until the EKF has converged.

**D-026 — E2E profile details** (2026-09-25, Claude proposal refining D-005; user-confirmed 2026-09-26)
CRC-8/SAE-J1850 (0x1D, init 0xFF, xorout 0xFF) over DataID low, DataID high, bytes 1..n-1; 4-bit counter 0..15; receiver max delta counter 1 (a single lost frame invalidates that cycle); timeout 3 × cycle, enforced both by `check_timeout()` and inside `check()` (a frame after a gap longer than the timeout resyncs as `INITIAL`, so a stalled sender never resumes as `OK`); `INITIAL` is not usable. Spec: `docs/e2e-profile.md`. Generated C is cross-checked against the Python reference.

**D-027 — codegen targets and vehicle-bus guard** (2026-09-25, Claude proposal refining D-003; user-confirmed 2026-09-26)
C is generated for RT_CORE, SAFETY, IO, CONN, HIL_SIM (`gen/c/<node>/`, cantools `use_float`, C99, no heap); HIL_SIM gets every message (restbus impersonation). LINUX and TESTER use the DBC/VSS at runtime and get Python/VSS only. The CL250 DID table goes to rt_core, conn (temporary tester, D-023) and hil_sim (ECU simulator), together with generated `vehicle_cl250_request_allowed()` (payload) and `vehicle_cl250_frame_allowed()` (raw ISO-TP Single Frame only) implementing D-020, which every vehicle-bus transmission must pass, and `vehicle_cl250_parse_response()` (checks SID 0x62 + DID echo). codegen holds a golden copy of the D-020 allow-list: the YAML policy may narrow it but never widen it (safety-reviewer finding).

**D-029 — Provisional base values until the measurement system exists** _(the safety-node speed bullet superseded by D-041 and D-048; Q-002 resolved by D-042; the RPM poll period superseded by D-052, the speed and RPM poll periods by D-053)_ (2026-09-25, user: "put the basic values that can be changed later; measurements come from a separate test device + server"; provisional answers to Q-014/Q-015; safety-reviewer findings applied)
- Poll periods: speed `0xF40D` 800 → **100 ms**, TPS `0xF411` 800 → **200 ms** (not a safety input), both `poll_period_verified: false` with `legacy_poll_period_ms: 800`; RPM 50 ms, coolant/battery 800 ms. `stale_after_ms` = 3 × poll period. A budget check requires sum(`assumed_round_trip_ms` / period) ≤ 0.8, with `assumed_round_trip_ms: 20` (provisional).
- `limits/platform_limits.yaml` (new; generated into `platform_limits.h` for rt_core/safety/hil_sim and `moto_defs/limits.py`):
  - DEFAULT µ **0.5**, clamp **0.1-1.2**, applied by both rt-core and safety-node. 1.2 is the ceiling ML may never raise.
  - µ rule: ESTIMATED/CLAMPED → clamp; DEFAULT → max(0.1, min(received, 0.5)); INVALID/RESERVED/unknown → the received value is ignored. The result is always finite.
  - **No default lean angle**: rt-core sends INVALID, and `LEAN_ANGLE_STATE` value 2 becomes RESERVED. Generated `platform_estimate_state_usable()` accepts only ESTIMATED/CLAMPED.
  - DEFAULT total mass **252 kg** (172 kg wet + 80 kg rider). Mass is not a Layer 1 cornering input; heavier is the conservative side elsewhere.
  - Speed: safety-node uses it only if VALID, E2E OK and effective age (AGE + time since the frame arrived) ≤ **400 ms**. It adds age × **5 m/s²** as an acceleration margin.
- Not decided here: what safety-node does when a value or the whole frame is not usable (Q-002 stays open). If it keeps computing, it uses these defaults.
- Every value carries `status: provisional` and a rule. Changing one is a `/signal-change` + safety-reviewer, and it is revisited with measured data. Why: consumers need concrete numbers now, both sides must use the same ones, and the conservative side is always chosen (hardware-architecture §5b.2).

**D-032 — BLE telemetry v3, raw IMU stream and the session upload path** (2026-09-27, Claude proposal from the data-pipeline task; user-confirmed 2026-09-28)
- BLE layouts stay single-sourced in `moto-connectivity-node/docs/ble_telemetry_packet_schema.json`:
  - **Telemetry v3** (37 B): node clock `deviceTimeMs`, per-signal ages (65535 = never received; valid bits from the generated `stale_after_ms`, D-029), and CAN/tester health (TWAI state, TEC/REC, bus-off count, unanswered DIDs, D-030 latch flags).

  - Fields carry `defsSignal` + `scale`, so decoders map them to `gen/python` DIDs without hand tables.
- **Raw IMU for data collection:**
  - connectivity-node samples an MPU-6050-compatible IMU (I2C on GPIO1/2, the legacy wiring) at 100 Hz, ±8 g / ±500 dps (4096 LSB/g, 65.5 LSB/(deg/s)).
  - It sends blocks of up to 10 samples at 10 Hz on a second characteristic. Each block has `deviceTimeMs`, `seq` and a tick index for exact loss counting.
  - Timer-driven task on core 0, static ring; the CAN poller never waits for it.
  - Offline analysis only: not a vehicle signal, not a safety input, not on the platform bus, no lean estimation (that stays in the rt-core EKF).
  - The part is provisional: the procurement list names MPU9250/LSM6DSO, and any part must deliver the schema scale.
- **Session files and upload:**
  - moto-mobile writes `meta.json`, `telemetry.csv` (v3 columns appended to the v2 ones, `raw_hex` authoritative), `events.csv` (including CAN health / MTU / IMU gap events), `summary.json` and `imu.csv`. Format: `moto-mobile/docs/session-format.md`.
  - The app uploads a session zip to moto-server `POST /sessions` (Bearer token, size limit, idempotent per `session_id`; recording and sharing work without a server).
- **moto-server v0:**
  - Re-decodes every row from `raw_hex` / raw IMU counts with the schema JSON.
  - Writes a validation report (JSON + text), Parquet with units in column names and `session_id` in every row, and a SQLite index under `$MOTO_DATA_DIR/sessions/<id>/{raw,parquet,report.json}`. MDF4 is an interface stub for now.

- Why: the phase0 plan (§3) needs timestamped CAN + 100 Hz IMU with loss accounting before any model work. The schema stays where the producer lives until Q-017 is decided.

**D-039 — Ç3 vehicle UDS client: design choices** (2026-09-29, user; items 4-5 from the safety review of rt-core#5)
1. **Temporary ISO codes.** gen/ lacks the generic ISO 14229 codes the client needs: the 0x22 request SID, the 0x7F negative response, and NRCs 0x78/0x7E/0x7F. Until a defs `/signal-change` generates them, they live in rt-core `src/features/uds/uds_iso14229.h`. That header holds no vehicle facts: IDs, DIDs, formulas and timings still come only from gen/. The positive 0x62 check stays in the generated `vehicle_cl250_parse_response()`.
2. **Sample store.** The per-DID samples (raw, physical, receive time) live in rt-core `services/vehicle_signals`. The poller is the single writer. Readers, including the future platform-bus republisher, never include `features/`. VALID/STALE is derived from `stale_after_ms` when a sample is read, and STALE stays sticky until the next write.
3. **NRC handling.** An NRC other than 0x78 ends the pending request, as the legacy code does. It is not a timeout, and it counts as proof that the ECU is present. NRC 0x7E or 0x7F means the session was lost, and it is re-established with 0x10 03 only.
4. **Fail-closed latch.** The client latches, sends nothing more and reports the reason (`uds_client_fault()`) when:
   - the link refuses a request
   - the `can_if` guard refuses a frame
   - any frame appears on `VEHICLE_CL250_REQUEST_ID` or `FALLBACK_REQUEST_ID`, which means a second tester (parity with connectivity-node's latch, D-030)

   A full TX mailbox is not a fault: the client waits.
5. **Out of scope.** N_As and bus-off handling come with the H7 FDCAN HAL (Ç1). The FDCAN acceptance filters must pass both request IDs.
- Why: the user preferred not to block Ç3 on a defs release. The store has to be readable by other features. The NRC rule keeps the verified legacy behaviour. The latch enforces D-021 in code.

**D-041 — Layer 1 cornering decision function; vehicle speed is not a safety-node input** (2026-09-30, user; ISSUES A-1; partly supersedes D-021 and the D-029 speed bullet)
1. **Physics.** In a steady turn (point mass, thin tyre) the moment balance about the contact line gives tan θ = v²/(g·R) = F_y/N. No sliding needs F_y ≤ µ·N, so the Layer 1 condition is **tan θ ≤ µ**. Speed and mass cancel: θ already carries v²/R, and m cancels in F_y/N. `v_max = √(µ·g·R)` (hardware-architecture §5b.2) is only needed when R is known and θ is not, which is a predictive (Layer 2/3) feature, not Layer 1.
2. **Decision function (safety-node):**
   - Inputs: θ = `LEAN_ANGLE` (0x020, deg) is usable only if the E2E status is OK (INITIAL is not usable, D-026), `LEAN_ANGLE_STATE` is ESTIMATED or CLAMPED, and θ is finite with |θ| ≤ 90°. µ_eff = `FRICTION_COEFF` (0x022) resolved by the D-029 rule, so it is always finite and within [0.1, 1.2]. Two thresholds k_yellow < k_red (dimensionless) come from `limits/platform_limits.yaml`.
   - u = tan|θ| / µ_eff (friction utilisation, dimensionless). The implementation is division-free: GREEN only if sin|θ| < k_yellow·µ_eff·cos|θ|, YELLOW only if sin|θ| < k_red·µ_eff·cos|θ|, otherwise RED. Any non-finite intermediate gives RED. Codegen checks 0 < k_yellow < k_red < 1.
   - Output level: GREEN if u < k_yellow, YELLOW if k_yellow ≤ u < k_red, RED if u ≥ k_red, with level hysteresis/debounce and an end-to-end latency budget from θ to the ring (values in the safety-node design, tested on HIL).
   - Output channels: the LED ring is the safety output. It is driven by safety-node, or by io-node from a safety-range E2E warning message whose loss shows UNAVAILABLE; **never by rt-core**, so that the D-042 fallback stays visible (the owner is Q-026). The HMI / voice warning is informational only (invariant 4).
   - ML (Layer 3): rt-core sends µ = min(µ_EKF, µ_ML), and ML never changes `FRICTION_COEFF_STATE` away from DEFAULT. Any ML threshold that reaches safety-node is applied as min(static, received), and the static value applies when it is absent. Nothing lifts µ above `friction_coeff_clamp_max` or raises k.
   - `LEAN_ANGLE` is defined as the **effective (resultant-force) lean**, computed in Layer 2. Tyre width makes the measured roll overstate it (conservative); hanging off makes roll understate it (not conservative), so roll alone is not enough.
   - When θ is not usable, D-042 applies.
3. **v1 is lateral only.** Combined braking or acceleration in a curve (friction circle √(tan²θ + (a_x/g)²) ≤ µ) is not checked yet. This is a documented limitation (Q-022). Until Q-022 is resolved, k_red must leave a longitudinal reserve (k_red = 0.8 leaves √(1 − 0.8²) = 0.6 of µ for braking). Road camber and crowned roads are also not modelled (tan(θ + β) would be needed); off-camber is the non-conservative case.
4. **Vehicle speed leaves Layer 1.** safety-node does not consume 0x021 `VehicleSpeed`, so the UDS poll → rt-core → E2E chain is not part of the cornering decision. rt-core still needs speed for the EKF lean estimate (Layer 2). 0x021 keeps its ID and E2E protection for its other consumers until a `/signal-change` decides otherwise. The speed rules in `platform_limits.yaml` (`vehicle_speed_max_age_ms`, `vehicle_speed_accel_margin_mps2`) are **re-scoped to rt-core** in that change: a lean computed from a speed older than `vehicle_speed_max_age_ms` is not sent as ESTIMATED/CLAMPED. Speed therefore still matters for safety, inside rt-core's Layer 2, and safety-node sees its loss as an unusable lean. Mass stays out of Layer 1 (D-029).
5. **Follow-ups:** the `/signal-change` adds k_yellow / k_red (provisional, conservative side), re-scopes the speed rules, decides 0x021's range and updates the `platform_limits.yaml` header (Q-002 is no longer open); the whole change needs safety-reviewer. The docs sync (ISSUES group 2) aligns hardware-architecture §5b.2 (and the conflicting LED-ring owner on the ring section), ARCHITECTURE §3/§4 (the Q-002 lines) and D-021's wording.
- Why: all three sources disagreed (§5b.2 lists mass, the limits file excludes it, D-021/D-029 give safety-node speed) and the function was not written down. With tan θ ≤ µ, speed and mass add a costly dependency and no information.

**D-042 — Q-002 resolved: safety-node gets its own minimal IMU as a fallback** (2026-09-30, user; ISSUES A-2)
1. safety-node gets its own small IMU (SPI; the part is chosen with the Group 7 hardware). The BOM gains one IMU (see ISSUES A-5).
2. **Speed-free fallback lean estimate:** in a steady turn the specific force is g/cos θ, so tan θ_eff = √((|f|/g)² − 1), clamped at 0. Using the full magnitude |f| rather than a_z alone never reads low under mounting tilt, braking dive or hanging off, and it also captures a_x. The gyro ratio θ ≈ atan(ω_y/ω_z) and the roll rate are combined in a complementary filter. The exact formulation is Q-023(6). This estimate is noisier and less accurate than the rt-core EKF and must be validated on HIL and in T4 field tests.
3. **Fallback only:** safety-node uses its own estimate only when rt-core's lean is not usable: E2E status other than OK (INITIAL included, D-026), a state other than ESTIMATED/CLAMPED, or the rt-core heartbeat not OK or its `NODE_MODE` ≠ NORMAL. In fallback, **µ_eff = min(D-029 result, `friction_coeff_default`)**, because 0x022 comes from the same EKF. The LED ring shows a distinct **DEGRADED** pattern, and safety-node reports `NODE_MODE` = DEGRADED in its heartbeat (0x082).
4. **UNAVAILABLE, never GREEN:** if neither lean source is usable (at boot, and after an own-IMU health fault: SPI/ID, self-test, saturation, stale data), the ring shows a distinct UNAVAILABLE pattern, never GREEN.
5. A continuous cross-check of the own estimate against rt-core's lean is not part of this decision (Q-023).
6. **Isolation:** the cornering decision now works without rt-core too (degraded). Invariant 3 already names the Raspi, phone, Wi-Fi, VSS and ML. The "works even if the main MCU crashes" claim in §5b.2 becomes true only with this fallback, and §5b.2's "no additional hardware" line is outdated (docs sync, group 2).
7. **Cost on the G474 (128 KB RAM / 512 KB flash):** about 3-5 KB flash and under 1 KB static RAM (driver, filter, no heap), 1 kHz SPI with DMA at under 2 % CPU. No platform-bus load.
- Why: before this decision every Layer 1 input came from rt-core, so the loss of rt-core ended the cornering function. safety-node now tolerates the loss of rt-core (detected by E2E and the heartbeat). It becomes an independent monitor of a wrong but valid rt-core lean (E2E OK, ESTIMATED, e.g. a diverged EKF) only with the cross-check (Q-023).

**D-046 — MISRA C:2012 and coverage floors are blocking CI gates** (2026-09-30, user: "whichever conforms to the standard"; ISSUES C-2; partly supersedes D-034)
1. **Hand-written MCU firmware** (rt-core now; safety-node, io-node and the hil-bench simulator firmware when they get code): cppcheck style + the MISRA C:2012 addon are **blocking** in CI. Compliance follows MISRA Compliance:2020: mandatory rules have no deviations; a required or advisory rule may be deviated only with a recorded `DEV-xxx` entry (rule, scope, rationale, compensating measure) in the repo's `misra/README.md`, and every inline suppression names its `DEV-xxx`. Host-only code (`hal/host`, `app/host`: POSIX, stdio) is not target firmware and is out of scope. ISO 26262-6 lists language subsets (Table 1) as highly recommended at every ASIL.
2. **Generated C (`moto-vehicle-defs` `gen/c`):** MISRA applies to generated code as well, and `gen/c` carries the D-020 gates and is linked by safety-node. So the MISRA addon is **blocking** on `gen/c` in the defs CI. Fixes go into the codegen templates, never into `gen/` by hand, and deviations are recorded in defs `misra/README.md`.
3. **connectivity-node** (temporary, not safety-related, ESP-IDF): cppcheck warning/portability/performance is **blocking**; the MISRA addon **reports only**, with ESP-IDF headers suppressed. Its vehicle-bus safety rests on the `gen/c` gates (item 2) and `tester_policy` (D-020, D-027).
4. **Coverage floors** (host tests, gcovr, target code only; host-only code excluded):
   - Every MCU repo: at least **95 % lines / 80 % branches**, blocking. The floors are a ratchet: they may be raised as tests grow, and lowering one needs the user's approval.
   - Safety-critical modules (the invariant 8 list: cornering/, safety-node decision logic, immobilizer, blind spot, watchdog/heartbeat, anomaly safety net, E2E, bootloader): target **100 % statement and branch** coverage. Every item left uncovered is justified in the module's README, and `safety-reviewer` checks the justification.
   - ISO 26262-6 (Table 9) sets no numeric thresholds: it asks for structural coverage (statement and branch; MC/DC highly recommended only at ASIL D) and a rationale for what is not covered. No ASIL has been assigned yet (no HARA), so MC/DC is not required now; if a HARA assigns ASIL D to a function, MC/DC is added for that module.
5. Rollout: rt-core already meets items 1 and 4 (general floors). The `gen/c` and connectivity-node CI steps are ISSUES group 3 (C-2). No MCU memory impact: these are CI-only checks.
- Why: the rt-core CI already enforced blocking MISRA and the 95/80 floors, but no decision recorded them, and D-034 still said MISRA only reports. The user chose the standard-conforming option.

**D-054 — CAN error state machine of rt-core (Ç1)** _(the item 8 read-out detailed by D-055)_ (2026-10-02, user; ISSUES D-2 and E-11 (1); confirms D-030's bus-off latch for rt-core)
1. **Placement.** rt-core gets `services/can_sm` (≈ AUTOSAR CanSM as a concept, next to `can_if` ≈ CanIf, D-006): a pure per-port core (ISO 11898-1 error active / error passive / bus-off, plus a latch) and glue over new HAL-free calls in `hal/can_port.h` (controller state, recovery, TX abort, acceptance filters; none of them sends a frame). `can_if` asks it before every write: a bus-off or latched port refuses with an I/O error that is never counted as a D-020 guard refusal, and the guard itself stays stateless. architecture-guard: no blocker.
2. **Bus-off recovery.** A bus-off aborts the port's pending TX (no stale frame after recovery) and is counted from a bus-off counter kept by the driver's ISR, so a short recover/re-bus-off between two steps is not missed. Recovery waits a backoff that starts at `bus_off_backoff_initial_ms` (1 s), doubles after every attempt up to `bus_off_backoff_max_ms` (30 s), and is back at 1 s once the port stayed on the bus for 30 s. The first attempt waits 1 s (conn's first attempt is immediate): the conservative side on the vehicle bus.
3. **Vehicle latch (option: RAM now, persistent later).** The vehicle port latches on its 5th bus-off since boot (D-030 parity, a local rt-core constant until it moves to `uds/vehicle_cl250.yaml`): off the vehicle bus until reboot. The count is in RAM; keeping it across a reset (a no-init or backup-SRAM section, like conn's RTC record) needs the linker script and comes with the board (Q-019). Accepted residual until then: a fault that causes a bus-off and then a reset gets 5 new bus-offs per boot. One physical bus-off counts once: the ISR counts entries only (IR.BO with PSR.BO = 1), and a bus-off seen by its flag before the ISR counter moved is a credit against that counter. Not chosen: a count that decays after 30 s on the bus (loosens D-030); no latch until it can persist.
4. **Platform bus (option: no latch, same backoff).** The platform port never latches and uses the same 1 s → 30 s schedule as local provisional values in rt-core, until the platform bus timing exists in moto-vehicle-defs. Why: it carries rt-core's own traffic to safety-node (heartbeat, E2E), and safety-node works without rt-core (invariant 3), so retrying is the safe side. Not chosen: an AUTOSAR-style fast-then-slow recovery (unmeasured numbers, more error frames on a broken bus); a defs change first.
5. **N_As.** Per port, frames pending with no TX confirmation for 1000 ms (the ISO 15765-2 N_As default, a generic ISO constant per D-030) are aborted; an ISO-TP link with a message under way ends it with N_TIMEOUT_A. This closes the uds README MINOR-B (an answer accepted by the link going out late after a bus stall). The vehicle port takes a new frame only when none is pending (one TX buffer), so a request never queues behind a stuck one.
6. **FDCAN2 TX (refines the uds README MINOR-4 requirement).** Dedicated TX buffers, one per safety-range ID (0x010-0x07F) and heartbeat, replace-on-new, so an E2E frame is never older than one write of its sender and never waits behind other traffic; everything else in a Tx FIFO, so frames of one ID keep their order (ISO-TP sequence numbers, E2E counters). Not chosen: Tx-Queue (priority) mode alone, which sends frames of one ID by buffer index and can reorder them once the put index wraps (safety-reviewer MAJOR-3). N_As is not the freshness bound of E2E frames.
7. **Filters and the comms task.** The acceptance filters are the `can_if` receiver table (vehicle: the response ID and every request and functional watch ID; platform: the server IDs, the gen/ platform UDS IDs into FIFO1); a port takes no new receiver after its filters are set. One comms pass (`app/comms`) runs the client before the server, for the host program and the H7 task alike. The H7 FDCAN port requirements are in moto-rt-core `src/hal/README.md`.
8. **Read-out (E-11 (1), option: a new platform DID).** A later `/signal-change` adds an rt-core health DID on the platform server: the D-053 step counters (`step_overruns`, `step_gap_max_ms`) and, per port, the CAN state, bus-off count, recoveries, N_As aborts and the latch, so a latched vehicle port is visible beyond STALE values and `VEHICLE_ECU_COMM_LOST`. Not chosen: XCP only (waits for xcp/); extending 0xFD00 (changes its length for existing readers).
- Unchanged: `tester_policy`, the golden D-020 copy, the `can_if` guard, one request in flight, the read-only ECU (D-037). rt-core v0.6.0: about +1.45 KB flash and +183 B RAM (M7 release). Fail-closed: invalid config, before init, unknown port, an unreadable controller state, and no recovery while a frame is still pending. architecture-guard no blocker; vss-schema-guardian CLEAN; safety-reviewer no blocker (MAJOR-1..3, m1, m2, m4-m6 and the NITs applied; m3 documented: init is boot only; delta review nothing MAJOR, its MINORs applied).

**D-055 — rt-core health DID and the vehicle bus-off DTC** (2026-10-02, user; ISSUES E-11 (1), E-12 (1); details D-054 item 8 and extends D-040 item 4's DTC set)
1. **DID 0xFD02 `RT_CORE_HEALTH` (option: 23 bytes, u16 counters).** A read-only record on rt-core's platform UDS server, big-endian like 0xFD01 and ISO 14229 data records. Byte 0 flags: `STEP_STATS_FRESH` (0x01), `VEHICLE_LATCHED` (0x02, set only when the vehicle `STATE` of the same response is LATCHED, for testers that want one bit). Bytes 1-4: the D-053 step counters `STEP_OVERRUNS`, `STEP_GAP_MAX_MS`. Bytes 5-13 the vehicle port, 14-22 the platform port: `STATE` (u8, `can_sm_state_t`: ERROR_ACTIVE 0, ERROR_PASSIVE 1, BUS_OFF 2, LATCHED 3, and UNKNOWN 0xFF for a port whose controller state cannot be read or before init, never its last state; a reader treats any value outside 0..3 as UNKNOWN, since 0 means healthy), then `BUS_OFFS`, `RECOVERIES`, `RECOVER_DEFERRED`, `NAS_ABORTS`. Appended after 0xFD14, so no existing index changes (MINOR, defs v0.4.0).
2. **Saturation.** Every multi-byte field is an unsigned value that saturates at its maximum and never wraps; rt-core's own counters are `uint32_t` and saturate too, so a reported value never goes down; the provider clamps each one to the field's `*_MAX` before packing, never truncates it. u16 is enough: the vehicle port latches at its 5th bus-off, and the platform port retries at most every 30 s once backed off (0xFFFF bus-offs ≈ 22 days of a dead bus). Not chosen: u32 counters (41 bytes, no practical gain); no separate latch bit.
3. **Freshness.** The step counters come from the vehicle UDS client; written more than `max_age_ms` (500, as 0xFD00) ago or never since boot, they read as their last values with `STEP_STATS_FRESH` clear (the client is not running, which 0xFD00 reports as NOT_RUNNING). The CAN fields are read from rt-core's CAN state machine at the time of the request.
4. **DTC 0xC00188 `VEHICLE_BUS_OFF_LATCHED` (option: while latched).** SAE J2012 U0001 (high speed CAN bus) with failure type 0x88 (bus off), as AUTOSAR CanSM reports a bus-off to Dem. It fails every pass while the vehicle port is latched (D-030, D-054), so a scan tool sees the root cause instead of only U0100 (ECU silent). It passes otherwise; a single bus-off that recovers leaves no DTC (the counters in 0xFD02 keep it). Clearing it (0x14) never releases the latch, and the DTC memory and the latch are both RAM until the board (D-040, D-054 item 3), so a reset clears both together. Not chosen: a DTC on every bus-off; no DTC.
5. **codegen.** A new DID encoding `record`: `{byte, mask}` flags or `{byte, length}` (1/2/4-byte) saturating unsigned fields; every byte belongs to one field. gen/ gives `*_BYTE`, `*_LENGTH`, `*_MAX`, `*_MASK` and the value names. codegen now refuses unknown field keys (it found a YAML comma that had cut 0xFD00 `FAULT`'s description).
6. **rt-core read path (architecture-guard: no blocker).** The UDS server never includes the UDS client: the client glue writes its step counters into `services/diag` with a timestamp every step, next to the vehicle-tester status, and the server reads the CAN state from `services/can_sm` directly (features → services; not copied into diag) and packs both with the gen/ field macros. `services/diag` stays free of `can_sm`: the server glue reports the DTC every pass next to `diag_supervise()`, whatever the client's state: failed while the vehicle port is LATCHED, passed in ERROR_ACTIVE / ERROR_PASSIVE / BUS_OFF, and no report at all while its state is UNKNOWN (never a pass on an unread state, never a latch nobody saw; the previous status stays, safety-reviewer m5). Within one response `VEHICLE_LATCHED` and the vehicle `STATE` come from one read, so they never disagree. `STEP_STATS_FRESH` is the only freshness signal of the step counters: wrap-safe age, a separate never-written flag (as for 0xFD00), and the client writes them every step, latched steps included. Memory estimate: about +0.3 KB flash and +0.1 KB RAM on rt-core (the 0x22 response buffers grow from 57 to 101 B with `max_read_dids` 4 × 23 B), +4 B flash and +1 B RAM for the DTC.
- Unchanged: the vehicle bus (one read-only tester, D-037), `tester_policy`, the golden D-020 copy, the `can_if` guard, 0xFD00/0xFD01 and their readers.
- safety-reviewer on defs#32: no blocker; MAJOR-1 (no UNKNOWN state, 0 reads as healthy) and m1-m4 plus the NITs applied in defs v0.4.0 (codegen also refuses bool values, non-`[A-Z][A-Z0-9_]*` names and duplicate codes in `values`). Provider requirements R1-R6 and tests go to rt-core with the defs bump.
- Why: D-054 left the latch visible only as STALE values and U0100, and the D-053 step counters only in the SIL summary (safety-reviewer MINOR-2 on rt-core#18).

**D-056 — Platform-bus republisher rules; generated C encoders round** (2026-10-03, user; ISSUES D-5; follows D-021, D-041, D-048, D-054 item 6)
1. **Encoders round and saturate (defs v0.5.0).** cantools' C `<msg>_<signal>_encode()` truncated toward zero while the Python reference rounds; in float this lost one raw step on 0x110 `BATTERY_VOLTAGE` (38863 of 65536 values) and `THROTTLE_POS` (49 of 256). codegen rewrites every encode body to round to nearest (halves away from zero), saturate at the C type's range and return 0 for NaN, so no input converts out of range (undefined in C; safety-reviewer MAJOR-2), with the cast on a plain object (MISRA 10.8, MAJOR-1); it stops on a body it does not know. Consumers never pre-round with scale literals (invariant 2) and still gate the physical range with `is_in_phys_range()`.
2. **Mapping (option: value 0, AGE 2550).** A `services/vehicle_signals` sample that is VALID (age ≤ the DID's `stale_after_ms`; for 0xF40D that is 300 ms, D-048) and inside the DBC signal's physical range is sent with its VALID bit set. NONE, STALE, a non-finite value or a value outside the physical range is sent as INVALID with the value field 0; no clamping (the 0xF40D range equals the 0x021 range, 0-255 km/h, so an out-of-range value is a fault, not a reading). 0x021 `VEHICLE_SPEED_AGE` is the sample age through the generated encode (nearest 10 ms; rt-core has no decode for a frame it sends, and rounding up would need a scale literal), saturating at 2550 ms; an INVALID speed sends 2550, so it never reads as fresh. The age counts from the send time of the DID's oldest unanswered read (D-051), before the ECU took the sample, so the half step it may round down stays inside that margin, and VALID always uses the unrounded age. The D-048 acceleration margin never applies to 0x021. `ECU_PRESENT` copies `vehicle_signals_ecu_present()`.
3. **Schedule.** 0x021 and 0x110 at their gen/ cycle times (50 ms), in the same comms pass, deadline-anchored; a late pass skips the missed cycles (no burst). The first frames go out at the first step, INVALID until samples exist.
4. **Order.** `comms_pass()`: vehicle `can_sm_step` → dispatch → `uds_client_step`, platform `can_sm_step` → dispatch → **republisher** → `uds_server_step`: same-pass samples, a current platform port state, and the E2E frame never waits behind server work. The comms pass period now bounds 0x021's freshness; the 20 ms EKF work (0x020) must not join this task (CLAUDE.md safety rule 4).
5. **E2E.** The module owns 0x021's `moto_e2e_tx_state_t`; the counter advances only when `can_if_write()` accepted the frame, so a refused write leaves no gap and a frame replaced in its buffer shows as a counter gap (a detected loss, D-026).
6. **FDCAN2 dedicated buffers.** 0x021 stays in the dedicated replace-on-new class of D-054 item 6 because of its safety-range ID, although SAFETY left its receivers (D-048). Features register such IDs at boot with `can_if_register_tx_dedicated()` (refused on the vehicle port, one TX buffer, D-021; refused once the port is sealed); `can_if_apply_filters()` hands the list to the new `can_port_set_tx_dedicated()` with the filters. A write to an ID whose previous frame is still pending cancels it and returns `CAN_PORT_TX_FULL` until the cancel completed (no wait loop); these replace cancels never count as N_As or `can_sm` aborts. At most 8 dedicated IDs per port (0x020-0x022, 0x081-0x085). HAL code never names an ID. Every other platform frame goes through the Tx FIFO **one element at a time**: `can_port_tx_free()` is true only while no FIFO element is pending, and a FIFO write while one is pending returns `CAN_PORT_TX_FULL`. This is the workaround of the M_CAN erratum "Tx FIFO message sequence inversion" (two pending FIFO frames, the first loses arbitration to a dedicated buffer, and the second goes out first); ISO-TP then sends one frame per comms pass. Whether the board's FDCAN has the erratum is confirmed against its ST errata sheet (ES0392 / ES0491) with Q-019; the rule stays until then.
7. **Placement and delivery.** `features/vehicle_republish/` (pure core + glue) over `services/{vehicle_signals,timebase,can_if}`; a shared `services/com` is extracted when a second sender (EKF 0x020/0x022, heartbeat 0x081) arrives, never by including this feature. Two rt-core PRs: the dedicated-buffer API first, then the republisher (rt-core v0.8.0 on defs v0.5.0); safety-reviewer on both.
- Unchanged: the vehicle bus (one read-only tester, D-037), `tester_policy`, the golden D-020 copy, the `can_if` vehicle guard.
- Why: the user chose the recommended option each time; architecture-guard (no blocker) asked for the PR split, out-of-range → INVALID instead of clamping, and the saturated AGE.

**D-058 — Phase 0 measurement tools in connectivity-node** (2026-10-03, user; hardware-integration.md §7 and §10 items 6-7; D-029, D-053 residual; Q-001)
1. **ECU round trip, per DID.** conn's poller measures, per DID, the time from the request's send (the TX call accepted the frame after the gate) to the step that drains its answer (positive response or an NRC other than 0x78). This is the round trip as the tester sees it, one step included, the same definition as `assumed_round_trip_ms`. A request that got 0x78 (responsePending) is counted in that DID's `nrc78` count and gives no round-trip sample. Kept since boot: min, max, sum and count (ms, saturating); consumers compute the average as sum / count.

The poller runs every `loop()` pass (period 0), so the gap includes the serial report, the other modules and the Arduino loop overhead, which the G0.1 loop-duration report does not.

The schema lives in defs (D-061); conn, moto-mobile and moto-server change together. The "drained" time includes loop latency; the schema says so.
4. **Q-001 listen-only capture in conn (option: separate build env).** New env `esp32-s3-devkitc-1-listen-only` with its own flag `CONN_CAN_LISTEN_ONLY=1` (not `CONN_VEHICLE_TESTER=0`, which means no TWAI driver at all, hardware-integration.md §11); the build fails if both the tester and the capture are enabled. - Unchanged: the vehicle bus (one read-only tester, D-037), `tester_policy`; the normal tester build gains only the counters.
- Implementation notes (2026-10-07, conn#10, safety-reviewer): (a) in listen-only mode the ESP32-S3 TWAI controller still sends a dominant error flag on a bus error (Espressif errata) unless `CONFIG_TWAI_ERRATA_FIX_LISTEN_ONLY_DOM=y`, which holds REC at 128 (error passive, recessive bits only) while listen-only runs (IDF 4.4.7 `twai_hal_start`). conn sets it in `sdkconfig.defaults` for every build, since the tester's Q-018 listen window uses the same mode, and CI checks the built `sdkconfig.h` of the capture and tester envs next to the `twai_transmit` check. **D-064 — rt-core heartbeat 0x081: NODE_MODE, ERROR_COUNT and UPTIME semantics** (2026-10-09, user; STATUS "Next up" 3, chosen over the EKF lean; D-005, D-026, D-042 item 3, D-056 item 7; architecture-guard on the plan)
1. **NODE_MODE (option: INIT / NORMAL / DEGRADED).** INIT for the frame built in rt-core's first comms step after the heartbeat opened (before any comms pass completed). DEGRADED while any rt-core DTC monitor's last result is failed (U0100-00 VEHICLE_ECU_COMM_LOST, U3000-00 VEHICLE_TESTER_LATCHED, U0001-88 VEHICLE_BUS_OFF_LATCHED) or one of these conditions holds although its monitor did not run (vehicle tester status latched or missing/stale, vehicle CAN port latched; architecture-guard MAJOR-1: U3000-00 supervision and U0001-88 run in the UDS server step). NORMAL otherwise. SAFE_STATE, BOOTLOADER and DIAGNOSTIC are not sent until defined; a non-default UDS session does not change NODE_MODE. Consequence: whenever the ECU stays silent (U0100-00), safety-node runs on its D-042 fallback lean and shows DEGRADED; how it returns is Q-023(4). Boot window (safety-reviewer MINOR-1): U0100-00 arms only `ECU_ABSENT_TIMEOUT_MS` (3 s) after the client opened, so with an ECU silent from boot the frames after INIT read NORMAL for up to 3 s ("no fault detected yet", not "ECU confirmed"), then DEGRADED.
2. **ERROR_COUNT (option: DTC failure onsets).** The number of times a DTC monitor's result went from passed (or not yet reported) to failed since boot, counted in `services/diag` apart from the DTC status bytes: a UDS 0x14 clear neither resets nor re-triggers it. Saturates at the signal maximum (DBC). A flapping monitor counts every onset. Not chosen: also counting bus-offs, N_As aborts and step overruns (noisy, overlaps the 0xFD02 health DID, D-055).
3. **UPTIME.** Whole seconds since boot, accumulated from wrap-safe timebase deltas so it never decreases (the ms timebase wraps after about 49.7 days; the DBC says a decrease means a restart). Saturates at the signal maximum.
4. **NORMAL does not attest the EKF.** The heartbeat is sent from the comms pass and proves that pass runs. Before rt-core publishes 0x020, the EKF task's alive supervision must also make NODE_MODE DEGRADED.
5. **Placement.** `features/heartbeat/` (pure core + glue), dedicated replace-on-new TX buffer (D-054 item 6), E2E commit on accepted frames only (D-056 item 5), `comms_pass()` order republisher → heartbeat → UDS server. The heartbeat is the second cyclic sender, so the shared `services/com` (cycle grid + send path) is extracted from the republisher in a behaviour-identical commit (D-056 item 7). No defs change: 0x081 and its E2E parameters exist since D-025/D-026.
- Why: safety-node's D-042 fallback switches on rt-core's heartbeat (E2E status and NODE_MODE), so rt-core needs a sender whose NORMAL means "no known fault" before any lean is published; tying DEGRADED to the existing DTC monitors keeps one definition of a fault.

**D-065 — rt-core EKF lean (0x020): algorithm, cross-task exchange, CLAMPED limit and PR order** (2026-10-09, user; STATUS "Next up" 3; hardware-architecture §5b.2 Layer 2; D-029, D-041, D-042, D-048, D-051, D-053 MINOR-4, D-056, D-064 item 4; architecture-guard on the plan)
1. **Algorithm (option: 2-state roll EKF).** `features/cornering/` estimates lean with an EKF whose state is [roll, roll-rate gyro bias]: predict with the gyro, measure roll from the coordinated-turn relation tan(roll) = v · yaw rate / g (an accelerometer tilt alone does not see a motorcycle's lean, since the resultant force stays in the bike's plane). Pitch is taken as about 0 (documented limit). The speed sample follows the `vehicle_speed` limits (age from its stamp at most 300 ms, plus age × 5 m/s²); without a usable speed the lean is INVALID. QUALITY comes from the roll variance; an innovation gate keeps a diverged filter from reading ESTIMATED; INVALID is sent with LEAN 0 and QUALITY 0, never state 2. Noise, convergence and quality-map constants are provisional until the T1/T4 measurements. Pure float32 core, non-finite values checked (MISRA Dir 4.1). Not chosen: a 7-state quaternion EKF (≈5-7 KB flash, ≈300 B RAM, harder to verify), a complementary filter (no variance for QUALITY, no bias tracking).
2. **Cross-task exchange and sender (option: wait-free triple buffer, comms sends 0x020).** The EKF runs in its own task above the comms task (CLAUDE.md rule 4). `services/snapshot` (generic single-producer/single-consumer triple buffer with an atomic index swap; the reader never retries or waits) carries comms → EKF the speed's physical value, absolute stamp and state (the EKF computes the age itself every step, so a stalled comms task makes the lean INVALID within 300 ms) and EKF → comms the lean, state, quality and output stamp. Barriers/atomics sit behind `hal/` with a host implementation. The comms pass sends 0x020 at its gen/ cycle through `services/com` (dedicated replace-on-new buffer, E2E state on the comms side, committed on `CAN_PORT_OK`, D-056 item 5); an output older than a budget derived from gen/ (cycle time + `CLIENT_STEP_MAX_MS` + jitter, below the 60 ms receiver timeout) goes out INVALID, since a stale replay would still pass E2E. `services/alive` (bumped after each complete EKF cycle) gives the heartbeat an `ekf_stalled` input through `app/comms`, which makes NODE_MODE DEGRADED (D-064 item 4), also while the EKF is registered but never ran. The IMU reaches the feature through `hal/imu.h` → `services/imu`; a stale or saturated sample gives INVALID. Not chosen: the EKF task sending 0x020 itself (a lock on the main-loop-only `can_if`, priority inversion).
3. **CLAMPED range (option: provisional defs limit).** A new provisional `cornering.lean_angle_clamp_max_deg` in `limits/platform_limits.yaml` (via `/signal-change`, defs MINOR release) is the physical range: |roll| above it is sent clamped with LEAN_ANGLE_STATE=CLAMPED. Its value and rationale are chosen in that change. Not chosen: the DBC's ±90° (no plausibility bound, CLAMPED would never occur).
4. **PR order (option: four PRs), each with `safety-reviewer` where cornering/ or the heartbeat changes:** (0) the defs limit and release; (1) rt-core `services/snapshot` + `services/alive` + the heartbeat's `ekf_stalled` input (stricter than "in the same PR as 0x020"); (2) the pure lean core and its tests; (3) `services/imu`, the 0x020 glue, the SIL IMU feed and the "never ran → DEGRADED" integration test. The task priority table (EKF > comms > anomaly/FFT/logging; IMU and FDCAN ISRs) is documented with PR (3) and checked on HIL once the board exists (Q-019).
- Why: the docs set 0x020's fields and the speed rules but not the estimator. The user chose the simplest verifiable filter (ISO 26262-6 §8), a lock-free exchange that keeps the EKF's timing free of the comms task (architecture-guard BLOCKERs: a speed snapshot carrying an age instead of a stamp, and a seqlock read by the higher-priority task), and a clamp from defs instead of a hand-picked number (invariant 2).
- Implementation (2026-10-09, v0.9.0, item 0 of the PR order): `lean_angle_clamp_max_deg` = 55.0 deg, provisional (user). safety-reviewer: no blocker. The D-041 decision is monotone in |lean| and RED is its top level, so codegen requires tan(clamp) > k_red · `friction_coeff_clamp_max` (43.83 deg): a clamped lean always reads RED and clamping never lowers the warning. It also keeps the clamp above atan(`friction_coeff_clamp_max`) = 50.19 deg (steady leans unclamped; availability, not safety) and below the `LEAN_ANGLE` maximum of 90 deg, on its 0.01 deg scale. rt-core (PR 3, MAJOR-1) sends INVALID for a non-finite roll, a failed innovation gate, a large variance or an unusable speed before it clamps, and clamps the output only, never the EKF state. A safety-node plausibility check on CLAMPED/ESTIMATED against this value is open (Q-029).
